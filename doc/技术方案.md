# 本地知识库系统 — 技术方案

## 一、需求回顾

| 维度 | 要点 |
|------|------|
| 文档量 | ~100GB，格式 doc / docx / pdf / ofd，以压缩包存储 |
| 目录结构 | 年 / 月 / 日 / 文档名 |
| 元数据 | item.csv（事项）、file_index.csv（文件映射）、item_with_opinions.csv（签阅记录） |
| 多租户 | 多部门 + 公共区，员工仅可访问本部门 + 公共区 |
| 用户体系 | user.csv，含 type/dept/username/password/role |
| 核心功能 | 文档导入（可选位置）、智能检索 + 溯源下载、知识图谱、结构化 Markdown 交叉引用 |

## 三、技术选型明细

### 3.1 后端框架 — Java Spring Boot 3

| 组件 | 选型 | 说明 |
|------|------|------|
| 框架 | **Spring Boot 3.x** | 主力技能栈，维护成本最低 |
| 安全 | **Spring Security** | RBAC 权限模型，方法级注解控制 |
| 数据访问 | **Spring Data JPA** + **MyBatis-Plus** | JPA 做基础 CRUD，MyBatis 做复杂查询 |
| API 文档 | **SpringDoc OpenAPI (Swagger 3)** | 自动生成接口文档 |
| 异步任务 | **Spring Task** + **RabbitMQ / Redis Queue** | 文档导入异步化 |

**选型理由：**

- 你是 Java 后端工程师，团队维护成本最低
- **OFD 格式是关键决策因素** — OFD（中国版式文档国标）仅 Java 有成熟开源库 `ofdrw`，Python/Go 几乎空白
- Spring Security 做 RBAC 权限成熟度业界公认

---

### 3.2 文档解析 — Java 进程内

| 格式 | 选型 | 许可证 | 说明 |
|------|------|--------|------|
| doc / docx | **Apache POI** | Apache 2.0 | 最成熟的 Java 文档库，支持段落/表格/图片提取 |
| PDF | **PDFBox** | Apache 2.0 | 开源免费，文本提取稳定 |
| OFD | **ofdrw** | Apache 2.0 | 国标版式文档解析，Java 唯一成熟选择 |
| 压缩包 | **commons-compress** | Apache 2.0 | 支持 zip / rar / 7z |
| OCR (扫描件) | **Tesseract** (via JavaCPP) | Apache 2.0 | 仅扫描件 PDF 需要，非必须 |

**解析流程：**

```
压缩包 → 解压 → 文件类型判断
  ├── .doc/.docx → Apache POI → 提取文本+表格
  ├── .pdf       → PDFBox      → 提取文本
  └── .ofd       → ofdrw       → 提取文本+签章信息
       │
       ▼
  纯文本 + 结构化 Markdown → 存入 MinIO
```

### 3.3 检索引擎 — Elasticsearch 8.x

| 功能 | 实现方式 |
|------|---------|
| 全文检索 | BM25 + **IK Analyzer** 中文分词 |
| 向量检索 | `dense_vector` 字段 + KNN 查询 |
| 混合检索 | **RRF (Reciprocal Rank Fusion)** 融合排序 |
| 权限过滤 | 查询时注入部门 filter，确保数据隔离 |
| 高亮 | ES 内置高亮，标注答案来源片段 |

**索引设计（核心字段）：**

```json
{
  "doc_index": {
    "mappings": {
      "properties": {
        "doc_id":           { "type": "keyword" },
        "file_name":        { "type": "keyword" },
        "dept_name":        { "type": "keyword" },
        "is_public":        { "type": "boolean" },
        "item_title":       { "type": "text", "analyzer": "ik_max_word" },
        "item_category":    { "type": "keyword" },
        "item_year":        { "type": "integer" },
        "content":          { "type": "text", "analyzer": "ik_max_word" },
        "content_vector":   { "type": "dense_vector", "dims": 1024 },
        "minio_path":       { "type": "keyword" },
        "created_at":       { "type": "date" }
      }
    }
  }
}
```

**选型理由：**

- 100GB 文档需要真正的倒排索引，轻量方案扛不住
- IK Analyzer 中文分词成熟，可自定义公文专用词典
- 8.x 自带向量检索，**BM25 + KNN 混合检索一个 ES 搞定**，不需要额外部署 Qdrant
- RRF 融合排序开箱即用

**为什么不用 Qdrant？**

需求中有精确关键词匹配 + 文件名溯源 + 元数据过滤（部门权限），这是 BM25 的典型强项、Qdrant 的弱项。Qdrant 可以作为纯向量层的备选，但 100GB 量级下 ES 单打完全够，引入两个存储得不偿失。

### 3.4 知识图谱 — Neo4j Community

**图谱模型：**

```cypher
// 节点类型
(:Department  { name })                   // 部门
(:Item        { id, title, category })    // 事项
(:Document    { id, name, path })         // 文件
(:User        { username, role })         // 用户
(:Opinion     { signer, time, content })  // 签阅意见
(:Category    { name, code })             // 分类

// 关系类型
(:Department) -[:OWNS]-> (:Item)
(:Item)       -[:CONTAINS]-> (:Document)
(:Document)   -[:REFERENCES]-> (:Document)    // 交叉引用
(:Item)       -[:BELONGS_TO]-> (:Category)
(:User)       -[:MEMBER_OF]-> (:Department)
(:User)       -[:SIGNED]-> (:Opinion)
(:Opinion)    -[:ON]-> (:Item)
```

**查询示例：**

```cypher
// 查询某个事项的完整脉络
MATCH (i:Item {id: "HZ000000700e74ef017b9ed1f47f7a8f"})
      -[:CONTAINS]-> (d:Document)
MATCH (i) -[:CONTAINS]-> (d2:Document)
      -[:REFERENCES]-> (ref:Document)
MATCH (o:Opinion) -[:ON]-> (i)
RETURN i, d, ref, o
```

**选型理由：**

- Cypher 图查询语言直观，业务开发效率高
- 交叉引用查询（"这个文件被哪些其他文件引用了"）是原生图遍历，关系数据库写递归 CTE 非常痛苦
- Community 版免费，满足当前规模

### 3.5 AI 服务 — Python FastAPI

| 功能 | 选型 | 说明 |
|------|------|------|
| Web 框架 | **FastAPI** | 异步高性能，自动 OpenAPI 文档 |
| LLM 调用 | **LangChain** + `langchain-ollama` | RAG 编排，Prompt 模板管理 |
| Embedding | **BAAI/bge-large-zh-v1.5** | 中文 Embedding 效果最好，Python 直接加载 |
| 图谱抽取 | **HanLP** + 自定义规则 | NER 命名实体识别 + 关系抽取 |

**为什么 AI 服务用 Python 而不是 Java 全栈？**

- 所有高质量中文 Embedding 模型（BGE、text2vec、m3e）都在 Python 生态
- LangChain / LlamaIndex 的 RAG 编排能力 Java 侧没有对等替代
- 作为独立服务部署，Java 通过 HTTP 调用，**不影响主体业务稳定性**
- 你懂 Python，可以维护

**RAG 问答流程：**

```
用户问题
  → ES 混合检索 (BM25 + KNN) → Top-K 文档片段
  → Neo4j 图谱扩展 → 补充关联文档
  → LangChain Prompt 模板组装
  → Ollama qwen3:14b-q4 生成答案
  → 返回：答案 + 引用来源 + 下载链接
```

**Embedding 生成：**

```
文档文本 → 分块(512 tokens, overlap 64)
  → bge-large-zh-v1.5 → 向量(1024维)
  → 写入 ES dense_vector 字段
```

### 3.6 本地大模型 — Ollama（CPU-Only）

**⚠️ 服务器无独立显卡**（AMD RYZEN AI MAX+ 395，Radeon 8060S 为集成显卡，Ollama 不支持其 GPU 加速），全部模型走 CPU 推理。

| 场景 | 推荐模型 | 内存占用 | 推理速度（16核CPU预估） | 说明 |
|------|---------|---------|------------------------|------|
| RAG 问答生成 | `qwen3:14b-q4_K_M` | ~9GB | 3~8 token/s | 量化后精度损失很小，中文能力够用 |
| 知识图谱抽取 | `qwen3:8b-q4_K_M` | ~5GB | 5~12 token/s | NER/关系抽取对模型大小不敏感 |
| Embedding | `bge-large-zh-v1.5`（Python 直载） | ~1.3GB | 实时 | 中文效果最优，不走 Ollama |
| 长文档摘要 | `qwen3:14b` (原始) | ~29GB | 1~3 token/s | 仅在精度要求极高时使用 |

**实际内存预算（总计 64GB）：**

```
Ollama qwen3:14b-q4    ████████████  9GB
Embedding (Python)      ██            2GB
Elasticsearch (Xmx)     ████████      6GB
Neo4j                   ██████        4GB
PostgreSQL              ████          3GB
Redis                   ██            1GB
MinIO                   ██            1GB
Spring Boot             ████████      6GB
Python FastAPI          ████          3GB
系统预留                 ██████████    8GB
──────────────────────────────────────────
剩余可用                 █████████████ 21GB
```

**结论：14B-Q4 是甜点**，64GB 完全扛得住整套环境 + 模型。32B 量化版也能跑但会挤占其他服务内存，不推荐。

**Ollama CPU 优化配置：**

```bash
# 启动 Ollama 容器时指定并行线程数
OLLAMA_NUM_PARALLEL=1        # 单机单用户，一次只处理一个请求
OLLAMA_MAX_LOADED_MODELS=1   # 内存有限，只加载当前使用的模型
OLLAMA_KEEP_ALIVE=5m         # 闲置 5 分钟后卸载模型释放内存
```

### 3.7 存储

| 层 | 选型 | 用途 |
|----|------|------|
| 文件存储 | **MinIO** | 原始文档、解析后 Markdown，S3 兼容，下载链接直出 |
| 业务数据库 | **PostgreSQL 15** | 用户、部门、CSV 导入元数据、导入任务状态 |
| 缓存 | **Redis** | Session、热点查询缓存、导入任务分布式锁 |

**选型理由：**

- **MinIO**：S3 兼容，部署简单（单二进制），下载链接自带过期机制，比 NFS/本地目录更适合 Web 访问
- **PostgreSQL**：稳定可靠，JSON 字段可灵活存储 CSV 元数据，比 MySQL 在复杂查询上更强
- **Redis**：标配，后续做分布式部署时可直接复用

### 3.9 为什么不选 AnythingLLM

| 需求 | AnythingLLM | 差距 |
|------|------------|------|
| 文档导入 doc/docx/pdf | ✅ | ❌ **不支持 OFD** |
| 全文检索 | 仅向量语义 | ❌ 无 BM25 关键词检索 |
| **知识图谱** | ❌ 完全没有 | ❌ 完全不支持 |
| 结构化 Markdown 交叉引用 | ❌ 没有 | ❌ 不支持 |
| 多部门 RBAC 权限 | ⚠️ workspace | ❌ 粒度粗，不匹配 |
| CSV 元数据导入 | ❌ 没有 | ❌ 无法导入 item.csv 等 |
| Ollama 本地模型 | ✅ | ✅ |

**结论：** AnythingLLM 适合"扔文档进去聊天"的通用场景，不适合本项目的 OFD 解析、知识图谱、RBAC 三大硬需求。

## 四、实体关系模型

```
item.csv                    file_index.csv              item_with_opinions.csv
┌──────────────────┐       ┌──────────────────┐       ┌──────────────────┐

│ 分类编号          │       └──────────────────┘       │ 签阅意见          │  │
│ 年度/字号         │                                  └──────────────────┘  │
│ 发文单位          │                                                       │
│ 事项类型          │       ┌──────────────────┐                             │
└──────────────────┘       │  实际文档文件      │                             │
         │                 │  年/月/日/xxx.PDF │                             │
         │                 └────────┬─────────┘                             │
```

## 五、文档导入流程（完整）

### 5.1 导入总览

```
导入压缩包
    │
    ├── 第1步：解压 + 文件分类
    │     ├── *.csv / *.xlsx           → 元数据文件
    │     └── *.doc/*.docx/*.pdf/*.ofd → 实际文档
    │
    ├── 第2步：解析元数据（先于文档解析）
    │     ├── item.csv                → item 表 + Neo4j (:Item) 节点
    │     ├── file_index.csv          → document 表 + Neo4j (:Document) 节点
    │     │                              + (:Item)-[:CONTAINS]->(:Document)
    │     └── item_with_opinions.csv  → opinion 表
    │                                    + Neo4j (:User)-[:SIGNED]->(:Opinion)-[:ON]->(:Item)
    │
    ├── 第3步：解析实际文档
    │     遍历文档文件
    │       ├── 与 file_index.csv 中的文件名/路径匹配 → 关联已有事项
    │       ├── 未匹配到 → 标记"未关联"，后续可手动绑定
    │       ├── 格式解析 → 提取纯文本 + 生成 Markdown
    │       ├── 原始文件 → MinIO（生成下载直链）
    │       ├── 文本分块 → Embedding → ES 索引
    │       └── 更新 document 表状态
    │
    └── 第4步：交叉引用检测
           Neo4j 中检测文档间引用关系
           例：文档A内容含"参见2021通1234号"
                 → 匹配到文档B的分类编号
                 → 创建 (:Document)-[:REFERENCES]->(:Document)
```

### 5.2 第1步：解压 + 文件分类

```
用户上传 zip/rar/7z
  → commons-compress 解压到临时目录
  → 遍历文件列表，按后缀分两路：

  元数据文件:                         实际文档:
    item.csv              →            001.PDF
    item.xlsx             →            002.DOC
    file_index.csv        →            003.DOCX
    file_index.xlsx       →            004.OFD
    item_with_opinions.csv →
    item_with_opinions.xlsx →

  注意：元数据也可能是 Excel 格式（需求原文："也可能是excel文件"）
  → 用 Apache POI 统一处理 .csv 和 .xlsx
```

### 5.3 第2步：解析元数据

#### 2a. item.csv → 事项元数据

```
逐行读取 item.csv:
  事项ID, 事项标题, 事项发起时间, 事项分类, 分类编号, 年度, 字号, 发文单位, 事项类型

每条记录:
  ┌─────────────────────────────────────┐
  │ PostgreSQL item 表                   │
  │  item_id     (PK, 来自CSV的事项ID)    │
  │  title       (事项标题)              │
  │  created_at  (事项发起时间)           │
  │  category    (事项分类)              │
  │  category_no (分类编号)              │
  │  year        (年度)                  │
  │  ref_no      (字号)                  │
  │  issuer      (发文单位)              │
  │  item_type   (事项类型: 收文/发文等)   │
  │  dept_name   (导入时用户选择的部门)    │
  │  is_public   (是否公共区)            │
  │  import_time (导入时间)              │
  └─────────────────────────────────────┘
         │
         ▼ 同步
  ┌─────────────────────────────────────┐
  │ Neo4j (:Item) 节点                   │
  │  { item_id, title, category, ... }  │
  └─────────────────────────────────────┘
```

#### 2b. file_index.csv → 文件映射

```
逐行读取 file_index.csv:
  文件ID, 文件名, 事项标题, 事项ID

每条记录:
  ┌─────────────────────────────────────┐
  │ PostgreSQL document 表               │
  │  file_id     (PK, 来自CSV的文件ID)    │
  │  file_name   (路径: 2021/09/01/xxx) │
  │  item_id     (FK → item.item_id)    │
  │  status      (expected / matched     │
  │               / missing / orphan)    │
  │  minio_path  (上传后回填)            │
  └─────────────────────────────────────┘
         │
         ▼ 同步
  ┌─────────────────────────────────────┐
  │ Neo4j (:Document) 节点               │
  │  { file_id, file_name, status }     │
  │                                     │
  │ Neo4j 关系:                         │
  │  (:Item)-[:CONTAINS]->(:Document)   │
  └─────────────────────────────────────┘

关键设计: status 字段
  "expected"  → CSV 记录存在，等待实际文档匹配
  "matched"   → 已找到对应实际文档，解析完成
  "missing"   → 有 CSV 记录但压缩包里没有对应文件
  "orphan"    → 有实际文件但 file_index.csv 中没有记录
```

#### 2c. item_with_opinions.csv → 签阅记录

```
逐行读取 item_with_opinions.csv:
  事项ID, 事项标题, 签阅时间, 签阅人, 签阅意见

每条记录:
  ┌─────────────────────────────────────┐
  │ PostgreSQL opinion 表                │
  │  id          (自增PK)               │
  │  item_id     (FK → item.item_id)    │
  │  signer      (签阅人)               │
  │  sign_time   (签阅时间)              │
  │  content     (签阅意见)              │
  └─────────────────────────────────────┘
         │
         ▼ 同步
  ┌─────────────────────────────────────┐
  │ Neo4j (:Opinion) 节点               │
  │  { signer, sign_time, content }    │
  │                                     │
  │ Neo4j 关系:                         │
  │  (:Item)-[:HAS_OPINION]->(:Opinion) │
  │                                     │
  │ 如果签阅人已在 user.csv 中存在:      │
  │  (:User {name: "张三"})             │
  │    -[:SIGNED]-> (:Opinion)          │
  │    -[:ON]-> (:Item)                 │
  └─────────────────────────────────────┘

注意: user.csv 中的用户名和签阅人姓名不一定完全一致
  → 先模糊匹配，匹配不上的只保留文本，不建立 (:User) 关联
```

### 5.4 第3步：解析实际文档

```
遍历压缩包中的文档文件 (*.doc/*.docx/*.pdf/*.ofd):

对每个文件:
  1. 提取文件名，在 document 表中按文件名匹配
     ├── 匹配成功:
     │     更新 status: "expected" → "matched"
     │     关联到对应 item + dept
     │
     └── 匹配失败:
           创建新的 document 记录，status = "orphan"
           归入"未关联"列表，前端提供手动绑定入口

  2. 格式解析:
     文件后缀 → 选择解析器
       .doc/.docx → Apache POI  → 文本 + 表格 + 图片位置标记
       .pdf       → PDFBox      → 文本（扫描件标记需OCR）
       .ofd       → ofdrw       → 文本 + 签章元信息

  3. 存储:
     原始文件 → MinIO: {bucket}/{dept}/{year}/{month}/{day}/{file_name}
                 生成预签名下载 URL，有效期 7 天（每次查询时刷新）
     解析文本 → MinIO: {bucket}/markdown/{file_id}.md
                 结构化 Markdown，含标题层级 + 表格 + 引用标记

  4. Embedding + 索引:
     文本分块 (512 tokens, overlap 64)
       → Python FastAPI: bge-large-zh-v1.5
       → 向量(1024维)
       → ES doc_index:
           {
             doc_id, file_name, dept_name, is_public,
             item_title, item_category, item_year,
             content (全文), content_vector (向量),
             minio_path (下载链接), chunk_index (分块序号)
           }

  5. 更新 PostgreSQL:
     UPDATE document SET status = 'matched', minio_path = ?, parsed_at = NOW()
```

### 5.5 第4步：交叉引用检测

```
在导入完成后批量执行（可异步）:

方式1 — 基于元数据规则匹配（优先，准确率高）:
  扫描所有 item 的分类编号 (如 "2021通1234")
    → 在 ES 中全文搜索其他文档是否包含该编号
    → 匹配到的创建引用关系

方式2 — 基于 NLP 实体识别（补充，覆盖非结构化引用）:
  Python: HanLP/HuggingFace NER
    → 识别文档中的"参见XXX"、"引用XXX"、"根据XXX号文"
    → 在 ES 中搜索被引用文档
    → 匹配到的创建引用关系

写入 Neo4j:
  MATCH (d1:Document {file_id: "..."}), (d2:Document {file_id: "..."})
  CREATE (d1)-[:REFERENCES {type: "explicit", context: "参见2021通1234号"}]->(d2)
```

### 5.6 数据落库分布总表

| 数据 | PostgreSQL | Neo4j | Elasticsearch | MinIO |
|------|-----------|-------|---------------|-------|
| item 元数据 | ✅ 主存储 | ✅ 节点 | ✅ 标题可搜 | ❌ |
| document 映射 | ✅ 主存储 | ✅ 节点 + CONTAINS 关系 | ✅ 文件名+元数据可搜 | ❌ |
| opinion 签阅 | ✅ 主存储 | ✅ 节点 + SIGNED/ON 关系 | ❌ | ❌ |
| 文档全文 | ❌ | ❌ | ✅ 分块索引(BM25) | ❌ |
| 文档向量 | ❌ | ❌ | ✅ dense_vector (KNN) | ❌ |
| 原始文件 | ❌ | ❌ | ❌ | ✅ 按部门/日期路径 |
| 解析后 Markdown | ❌ | ❌ | ❌ | ✅ markdown/{file_id} |

### 5.7 边界情况处理

| 情况 | 处理策略 |
|------|---------|
| **有 CSV 但缺实际文档** | 元数据照常入库，document.status = `missing`，图谱中灰色显示 |
| **有实际文档但缺 CSV** | 照样解析索引，status = `orphan`，前端提供手动绑定入口 |
| **file_index 路径与压缩包内文件名不一致** | 先按文件名（去掉路径前缀）模糊匹配；匹配不上的进人工核对队列 |
| **签阅记录的 item_id 在 item.csv 中不存在** | 签阅暂存但跳过建图关系，导入完成后统一报出异常数据列表 |
| **同一事项重复导入** | 按 item_id 做 upsert（更新元数据，不重复建节点）；签阅记录追加去重 |
| **压缩包内嵌子目录** | 递归遍历，文件名保留相对路径作为标识 |

### 5.9 导入注意事项

**CSV 编码问题：**

政府公文 CSV 文件常见 GBK / GB2312 编码，直接按 UTF-8 读取会乱码。处理策略：

```java
// Java 端用 juniversalchardet 自动检测编码
byte[] raw = Files.readAllBytes(csvFile.toPath());
String encoding = UniversalDetector.detectCharset(raw); // → "GBK" / "UTF-8" / ...
String content = new String(raw, Charset.forName(encoding));
```

**PostgreSQL + Neo4j + ES 三写一致性：**

```
写入策略：
  1. 以 PostgreSQL 为权威数据源（主存储）
  2. Neo4j 和 ES 为派生数据（可重建）
  3. PG 写入成功 = 事务提交
  4. Neo4j/ES 写入失败 → 记录到 retry_queue 表
  5. 后台定时任务扫描 retry_queue，异步补偿
  6. 极端情况下可通过 PG 全量重建 Neo4j 和 ES
```

**导入性能估算（CPU-Only 单机）：**

| 阶段 | 速度 | 100GB 预估耗时 |
|------|------|---------------|
| 解压 | ~100MB/s | ~20 分钟 |
| 文本解析（doc/docx/pdf） | ~20MB/s | ~1.5 小时 |
| OFD 解析 | ~5MB/s | 视 OFD 占比而定 |
| Embedding（bge-large CPU） | ~200 token/s | ~4~8 小时 |
| ES 批量索引 | ~5000 doc/s | ~30 分钟 |
| 交叉引用检测 | 取决于文档量 | ~1 小时 |

> 首次全量导入预计 **6~12 小时**，建议夜间执行。增量导入（单压缩包）通常 5~15 分钟。

```
5. 后期可切换到数据库管理，user.csv 仅首次导入
```

### 8.7 CPU 推理注意事项

| 要点 | 说明 |
|------|------|
| 首次查询慢 | 模型从磁盘加载到内存需 5~15 秒，后续查询热加载 |
| 并发限制 | `OLLAMA_NUM_PARALLEL=1`，同一时间只处理一个 LLM 请求 |
| 长文档问答 | 14B-Q4 生成速度约 3~8 token/s，一个回答 500 token 约需 1~3 分钟 |
| 文档导入不阻塞 | Embedding 用 bge-m3 走 CPU 也很快，导入时问答可能变慢 |
| 后续可加 GPU | 机器有 PCIe 插槽的话，日后加一张 RTX 4060Ti 16G 就能跑 qwen3:14b 原生精度 |

### 8.8 磁盘容量估算

| 数据 | 估算大小 | 说明 |
|------|---------|------|
| 原始文档 | ~100GB | 压缩包内的 doc/docx/pdf/ofd |
| MinIO 存储 | ~150GB | 原始文件 + 解析后 Markdown（约 1.5x） |
| ES 索引 | ~80~120GB | 全文索引约为原文的 1~1.2x；向量(dense_vector)另占 20~40GB |
| PostgreSQL 数据 | ~5GB | 元数据 + 用户 + 任务记录 |
| Neo4j 数据 | ~5GB | 图节点 + 关系 + 索引 |
| Redis | ~0.5GB | 缓存 + Session |
| Ollama 模型文件 | ~15GB | qwen3:14b-q4(~9GB) + qwen3:8b-q4(~5GB) |
| **总计** | **~350~400GB** | 建议分配 **500GB 以上** 留余量 |

### 8.9 注意事项

- **不要用 `latest` 标签锁定生产环境**，ES 升级可能不兼容索引格式
- **MinIO 数据盘独立挂载**，不要和系统盘共用
- ES 的 `vm.max_map_count` 需要设置：`sudo sysctl -w vm.max_map_count=262144`
- Ollama 模型文件较大（Q4 约 9GB），首次 `pull` 需要等待下载
- **生产环境端口安全**：仅 nginx(80/443) 需对外暴露，其他服务端口（5432/6379/9200/7474/9000/11434/8080/8000/3000）应在 docker-compose 中去掉 `ports` 映射，或绑定 `127.0.0.1`

## 九、关键技术风险与应对

| 风险 | 概率 | 影响 | 应对措施 |
|------|------|------|---------|
| OFD 解析质量不足 | 中 | 高 | 提前做 PoC，取 10 份真实 OFD 测试 ofdrw 提取效果 |
| 100GB 导入耗时过长 | 高 | 中 | 异步批量处理 + 并行解析 + 断点续传 |
| 中文检索精度不够 | 中 | 中 | IK 自定义词典（公文术语） + 向量检索兜底 |
| 知识图谱自动抽取准确率低 | 高 | 中 | **以 CSV 元数据建图为主**，NLP 自动抽取为补充 |
| **CPU 推理速度不足** | 高 | 中 | 14B-Q4 量化 + `num_parallel=1` + `num_ctx=4096`；回答 1~3 分钟；后续可插独立显卡 |
| CSV 文件编码非 UTF-8 | 高 | 低 | 政府公文 CSV 常见 GBK/GB2312，用 `juniversalchardet` 自动检测编码再解析 |
| ES + Neo4j + PG 三写一致性 | 中 | 中 | 以 PostgreSQL 为准；Neo4j/ES 写入失败时记录补偿任务，后台异步重试 |
| OFD 电子签章验证 | 低 | 低 | 初期仅提取签章元信息，不做验签 |
