# 智能问答联调排错记录

## 背景

本地知识库系统的智能问答功能涉及 **4 层调用链**：

```
浏览器 → Vue前端(:3000) → Java后端(:8080) → Python AI服务(:8000) → Ollama容器(:11434)
                                                      ↓
                                              Elasticsearch(:9200)
```

每次发消息，后端执行三步：文本向量化 → ES 检索相关文档 → Ollama LLM 生成回答。

联调过程中遇到一系列问题，覆盖了 Docker 配置、Spring Security、HTTP 客户端兼容性、超时设置等多个层面。

## 详细排错过程

### 问题 1：ES 索引创建失败

**现象：**
```
co.elastic.clients.elasticsearch._types.ElasticsearchException:
analyzer [ik_max_word] has not been configured in mappings
```

**排错：**
1. 检查 ES 容器 → IK 插件未安装（`elasticsearch-plugin` 不认短名 `analysis-ik`）
2. 写 Dockerfile 内置 IK → 构建成功但索引创建仍失败
3. 报错变为 `surname.dic not found` → 发现 volume 挂载 `./config/es:/usr/share/elasticsearch/config/analysis-ik:ro` 用宿主机空目录**整体覆盖**了插件的默认词典目录

**解决：**
- 创建 `docker/config/es/Dockerfile`：在构建时安装 IK + COPY 自定义词典到镜像内
- 去掉 `docker-compose.yml` 中覆盖 `analysis-ik` 目录的 volume 挂载
- 使用 `build: ./config/es` 替代 `image:` 直接拉官方镜像

**关键知识点：** Docker volume 挂载是**目录级别替换**，不是文件级合并。挂载 `/foo` 到容器内的 `/bar` 后，`/bar` 原有的所有内容都会被宿主机 `/foo` 覆盖。

### 问题 2：Ollama 内存不足

**现象：**
```
model requires more system memory (9.4 GiB) than is available (5.2 GiB)
```

**排错：**
- Ollama 容器 `mem_limit: 16g`，但实际可用仅 5.2GB
- 宿主机 16GB RAM，Docker/WSL2 分配约 8GB
- PG + Redis + ES + Neo4j 占用约 3GB，留给 Ollama 的 <6GB
- 14B-Q4 模型加载需 9.4GB

**解决：**
- 切换到 `qwen3:8b-q4_K_M`（~5.5GB）
- 配置 `OLLAMA_MAX_LOADED_MODELS=1` + `OLLAMA_KEEP_ALIVE=5m` 避免多模型同时驻留
- 给 ES 降配 `-Xms1g -Xmx1g` 释放 1GB

**关键知识点：** Docker `mem_limit` 是上限不是保底。实际可用内存取决于 Docker Engine 分配总量减去其他容器占用。Ollama 模型的 `size` 字段是磁盘占用，运行时内存消耗通常 > 磁盘大小（需加载完整计算图）。

### 问题 3：无法初始化管理员

**现象：** `POST /api/users/init` 返回 403 Forbidden

**排错：**
1. 检查 `SecurityConfig.java` → 已添加 `.requestMatchers("/api/users/init").permitAll()`
2. URL 白名单不生效 → 发现 `@EnableMethodSecurity` 开启了方法级注解
3. `UserController` 类上有 `@PreAuthorize("hasRole('ADMIN')")` —— **方法级安全优先于 URL 级安全**

**解决：**
```java
// URL 白名单 (SecurityConfig) —— 第一道防线
.requestMatchers("/api/users/init").permitAll()

// 方法级注解 (UserController) —— 需要显式覆盖
@PostMapping("/init")
@PreAuthorize("permitAll()")  // 覆盖类级 ADMIN 限制
public ApiResponse<...> initAdmin(...) { ... }
```

**关键知识点：** Spring Security 的执行链是 `Filter → Interceptor → Method Security`。URL 规则和 `@PreAuthorize` 是独立的两个维度，后者不因前者放行而自动跳过。**方法级注解的优先级高于 URL 规则**，因为它在更靠近实际方法调用的位置执行。

**面试扩展：** Spring Security 多层防护模型：
```
请求 → SecurityFilterChain (URL过滤) → Authentication (认证) → AuthorizationFilter (授权) → MethodInterceptor (@PreAuthorize)
```
每一层都可以独立拒绝请求。实际项目中，URL 规则做粗粒度控制（哪些路径需要什么角色），方法注解做细粒度控制（方法级别的权限 + 数据权限）。

### 问题 4：Java HTTP 客户端与 Python ASGI 的兼容性

**现象：** AI 服务返回 `422 Unprocessable Entity`，uvicorn 日志显示 `WARNING: Unsupported upgrade request.`

**排错：**
1. 在浏览器层 `curl` 直调 Python `/embed` 和 `/chat` → 正常 → 排除 AI 服务问题
2. 在 Ollama 层 `curl` 直调 → 正常 → 排除 Ollama 问题
3. 检查 Java 后端日志 → `log.error("Embedding 生成失败", e)` → 自产自销了错误，没暴露根因
4. 定位到 `AIClient.java`：`java.net.http.HttpClient` **Java 11+ 默认走 HTTP/2**

**根因：** Java 11 的 `HttpClient` 默认使用 HTTP/2。当目标服务器不支持 H2 时，客户端发送带 `Upgrade: h2c` 头的 HTTP/1.1 请求尝试协议升级。Uvicorn 不理解此升级请求，将整个 HTTP 报文当作非法请求处理，因此 Pydantic 收到的 body 为 null → 422。

**解决：** 设置 `HttpClient.newBuilder().version(HttpClient.Version.HTTP_1_1)`。

**关键知识点：** HTTP/2 升级机制 (h2c upgrade) 在 HTTP/1.1 中通过 `Upgrade` 头实现。CLI 工具（curl）和 Python `requests` 库默认 HTTP/1.1；Java 11 `HttpClient` 默认 HTTP/2。跨语言 HTTP 通信时，协议版本不一致是常见踩坑点。

### 问题 5：RestClient 请求体丢失

**现象：** 换成 Spring `RestClient` 后，AI 服务返回 `{"detail":[{"type":"missing","loc":["body"],"msg":"Field required","input":null}]}` ——请求体完全为空。

**排错：**
1. 日志显示请求已发出，URL 正确
2. Python 侧 `loc: ["body"]` 表示 FastAPI 没收到任何请求体
3. 检查 `JdkClientHttpRequestFactory` + `RestClient.body(obj)` → **`JdkClientHttpRequestFactory` 不自动处理 POJO 序列化**

**解决：** 手动序列化为 JSON 字符串：
```java
// ❌ 依赖自动序列化（不工作）
.body(req)

// ✅ 手动序列化
String json = objectMapper.writeValueAsString(req);
.body(json)
```

**关键知识点：** Spring `RestClient.body(Object)` 的序列化依赖于注册的 `HttpMessageConverter`。使用自定义 `ClientHttpRequestFactory` 时，转换器链可能不完整。传 `String` 类型可绕过转换器，直接以字节形式发送。

### 问题 6：OkHttp 超时导致对话中断

**现象：**
```
org.springframework.web.client.ResourceAccessException: I/O error on POST request: timeout
Caused by: java.net.SocketTimeoutException: timeout
```

**排错：**
1. Ollama 直调需 ~87 秒（42 秒加载模型 + 45 秒生成）
2. 但超时发生在发出请求后仅 ~10 秒
3. `spring.http.client.read-timeout: 5m` 配置无效 → 该配置只对自动配置的 `RestClientBuilder` 生效
4. 当前使用的 `RestClient.builder().requestFactory(factory).build()` 不走自动配置
5. OkHttp 作为传递依赖被 Spring 自动检测并使用，其默认 readTimeout = **10 秒**

**解决：**
```java
// 使用 JDK 原生 HttpURLConnection（不走 OkHttp），显式设超时
var factory = new SimpleClientHttpRequestFactory();
factory.setConnectTimeout(Duration.ofSeconds(10));
factory.setReadTimeout(Duration.ofMinutes(5));
this.restClient = RestClient.builder().requestFactory(factory).build();
```

**关键知识点：**
- Spring Boot 的 HTTP 客户端选择优先级：OkHttp3 > HttpComponents > JDK HttpClient > Simple (HttpURLConnection)
- OkHttp 作为传递依赖（Elasticsearch client 引入）自动成为 `RestClient` 的底层实现
- `SimpleClientHttpRequestFactory` 基于 JDK 的 `HttpURLConnection`，无额外依赖，行为最可预测
- **CPU 推理场景**下，HTTP 超时必须覆盖模型加载时间 + 推理生成时间

## 经验总结

| 领域 | 教训 |
|------|------|
| **Docker** | Volume 挂载是目录级替换，不是文件级合并；Dockerfile 构建优于运行时手动配置 |
| **Spring Security** | URL 规则和 `@PreAuthorize` 是两道独立的防线，方法注解优先级更高 |
| **HTTP 协议** | Java 11 HttpClient 默认 HTTP/2；跨语言 HTTP 通信首选 HTTP/1.1 |
| **序列化** | 不依赖框架自动序列化，关键路径手动 JSON 更可控 |
| **超时** | AI/LLM 推理场景超时必须覆盖模型加载+生成，建议 ≥3 分钟 |
| **日志设计** | `catch{log.error; return fallback;}` 会隐藏真实错误，调试阶段应先暴露异常 |
| **内存规划** | 本地 LLM 部署前先评估 `运行内存 = 模型大小 × 1.2 + 上下文开销`，确认 Docker 实际分配量 |

## 面试可展开的技术点

1. **微服务调用链调试**：如何从浏览器 F12 → 后端日志 → AI 服务日志 → Ollama API 逐层定位？每一层用什么工具？

2. **Spring Security 双层防护**：URL 规则 vs 方法注解的执行顺序、各自适用场景、如何设计权限分层

3. **HTTP 协议演进**：HTTP/1.1 Keep-Alive vs HTTP/2 多路复用 vs h2c 升级机制；为什么升级请求在某些服务器上被视为非法？

4. **Java HTTP 客户端选型**：JDK HttpClient vs OkHttp vs Apache HttpComponents vs RestTemplate vs RestClient vs WebClient ——各自的超时配置、连接池、协议支持

5. **Docker 资源管理**：mem_limit 和实际可用内存的关系；WSL2 的内存分配机制；如何规划容器化本地 LLM 部署的内存预算

6. **LLM 推理优化**：KV Cache、量化精度(Q4_K_M)、上下文长度(num_ctx)、推理并发(parallel=1)对内存和速度的影响
